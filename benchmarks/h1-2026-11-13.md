# HTTP/1.1 benchmark — 2026-11-13

Optimized h1 improves large downloads over the same DPDK TCP transport;
small requests and uploads do not show a comparable gain.

## Results

Each number is the median of the three per-run statistics, not a pooled
percentile. Latency is connect through fully collected response body.
Concurrency is one, with a fresh TCP connection for every request.

| Workload | Optimized h1 / DPDK p50 µs | Hyper / DPDK p50 µs | Hyper / kernel p50 µs | Optimized h1 / DPDK p99 µs |
|---|---:|---:|---:|---:|
| GET 64 B | 29.58 | 26.58 | 39.75 | 38.75 |
| GET 16 KiB | 33.88 | 36.42 | 47.29 | 54.83 |
| GET 1 MiB | 368.58 | 559.75 | 567.21 | 444.46 |
| POST 64 B | 27.12 | 25.79 | 40.88 | 39.58 |
| POST 16 KiB | 50.71 | 53.58 | 44.58 | 62.71 |
| POST 1 MiB | 1301.67 | 1311.92 | 803.38 | 1377.75 |

For 1 MiB GETs, payload throughput was **22.51 Gbit/s optimized h1**, versus
**14.97 Gbit/s hyper/DPDK** and **14.79 Gbit/s hyper/kernel**. Optimized h1
increased throughput by approximately **50%** over hyper/DPDK and reduced
p50 latency by **34%**. For 1 MiB POSTs, the corresponding rates were
**6.43**, **6.38**, and **10.36 Gbit/s**. Small differences are not evidence
of a repeatable speedup; this run provides no confidence intervals.

## Methodology

- Release build, Rust 1.96.1, DPDK 22.11.11, Linux aarch64 under Docker Desktop
  on Apple hardware, 18 virtual CPUs visible.
- Same single-threaded hyper HTTP/1.1 server, pinned to CPU 2. Client runtime
  pinned to CPU 0; DPDK additionally busy-polls its worker on CPU 1.
- One veth link across a network namespace, MTU 1500. TX checksum offload,
  TSO, GSO and GRO disabled on both ends. DPDK uses `net_af_packet`.
- Plaintext only; NODELAY enabled, cork disabled. `Connection: close` on
  requests and responses. No connection reuse, TLS, DNS, or concurrency.
- Optimized path calls the real `Client::request::<Raw, Raw>` API, including
  its routing, encoding and response collection. Hyper/DPDK uses the same
  `TcpStream` and worker via the AsyncRead/AsyncWrite interface. It is a
  comparison against hyper, not a measurement of an older git revision.
- Three runs per backend, six workloads, 20 warmups then 300 timed requests
  each. All 16,200 timed requests completed; all 17,280 requests including
  warmups had their status, version and response bytes verified. POST
  payloads were also verified by the server before acknowledging them.
- Request construction and client-side response validation are outside the
  timing window. Connect, HTTP exchange and collection are inside it;
  TCP teardown is not awaited. Payload throughput and requests/sec use the
  sum of request durations, excluding validation and inter-request gaps.
- Server payload buffers and client upload buffers are preallocated.
- DPDK modes alternate order across repetitions. Kernel runs precede DPDK
  runs, so time/order drift remains possible. Each DPDK process has a distinct
  source IP to avoid prior processes' TCP state affecting reconnects.
- One-second outliers appeared in an initial five-sample smoke run sharing
  source IPs; they disappeared after source-IP isolation. The saved full run
  uses isolation. This is not proof of the smoke-run outliers' root cause.

These are virtual-link results, not physical NIC throughput or CPU-efficiency
measurements. DPDK uses an additional busy-polling core. Bulk upload performance
remains below the kernel baseline; profiling that path is a useful next step.

## Reproduce

In a privileged DPDK devcontainer with `ethtool` installed:

```sh
BENCH_H1_ROUNDS=300 BENCH_H1_WARMUP=20 BENCH_H1_REPEATS=3 \
  bash scripts/bench_h1.sh > benchmarks/h1-results.tsv 2> benchmarks/h1-results.log
```

The script owns dedicated `h1bench0` / `httpio-h1-bench` network resources,
refuses preexisting names and cleans them up on exit. It requires CPUs 0–2.
For this run the existing devcontainer lacked namespace permissions, so an
isolated temporary privileged container used the same image and build volume,
with `--network none`. `BENCH_H1_SKIP_BUILD=1` used the release binary already
built in the devcontainer; ethtool was mounted read-only from that container.

The example also builds without DPDK and supports `server IP` and `kernel IP`
modes there. DPDK modes explicitly require a DPDK build.
